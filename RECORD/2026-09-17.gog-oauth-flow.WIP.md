# GOG OAuth2 authentication

- **Status:** WIP
- **Started:** 2026-09-17
- **Roadmap:** ROADMAP/2026-09-16/02-core.md (`auth`)

## 2026-09-17 00:10 — The flow, minus the live verification

Implemented the authorization-code flow decided in
`RECORD/2026-09-16.gog-login-flow-decision.completed.md`: the user logs in in a
browser and pastes back the address GOG lands them on, and the code→token
exchange runs locally so the client secret never leaves the machine.

New in `core`:

- `http` — an `HttpClient` trait (`get` returning status plus body) with a
  blocking `ureq` implementation, 30 second per-request deadline. Everything the
  auth flow and, later, the catalog and downloader do goes through the trait, so
  they are testable with no network. Non-2xx responses are returned rather than
  raised, because GOG puts its error details in the body. `http::redact` strips
  query strings, and every error message about a URL goes through it — a token
  request carries the client secret and the code in its query.
- `auth` — `Credentials` (with `authorization_url`), `extract_code`,
  `exchange_code`, `refresh` and `TokenSet`.
  - `extract_code` accepts the whole pasted address or a bare code, reports
    GOG's own `error`/`error_description` when the login was denied, and refuses
    anything that does not look like a code instead of sending it to GOG.
  - Query values are encoded leaving the RFC 3986 unreserved set (`-._~`) alone.
    Encoding those too is legal, but GOG compares `redirect_uri` against the one
    the client is registered with, so the value it receives should be the obvious
    spelling. This was a real bug in the first draft: it produced
    `redirect_uri=https%3A%2F%2Fembed%2Egog%2Ecom%2F…`.
  - `TokenSet::is_expired` keeps a minute of margin, so a request never starts on
    a token that expires mid-flight. `refresh` exists because GOG rotates refresh
    tokens; wiring it into a session belongs to `tok`.
  - `Credentials` and `TokenSet` have hand-written `Debug` impls that redact the
    secret and the tokens: `02-core.md` requires that tokens never reach logs, and
    a derived `Debug` in a `tracing` call is the obvious way to break that.
- `config` — an `[auth]` section (`client_id`, `client_secret`, `redirect_uri`),
  with `GOG_CLIENT_ID` and `GOG_CLIENT_SECRET` winning over the file so a shared
  machine can keep them out of a config the kids can read. `Config::to_toml` still
  writes the secret, but `gamestore config` prints through
  `to_toml_redacted`, since that command is run on a TV in the living room.

**No credentials are baked in.** Open question 3 (ship the well-known Galaxy
credentials or require the user's own) stays open, and the code works either way:
answering it later only adds a default.

New in `cli`: `gamestore login` prints the authorization URL, reads the pasted
address, exchanges it, and reports the GOG user id and how long the access token
is good for. It stores nothing — persistence is `tok`, and writing tokens to a
plain file in the meantime would be worse than not having them.

### What is verified, and what is not

35 tests pass on Linux, covering URL construction, code extraction (address, bare
code, denied login, no code, garbage), both grant types, expiry arithmetic, a
rejected exchange, an unreadable response, and that neither secrets nor tokens
appear in `Debug` output. The CLI was exercised by hand for all four outcomes.

**Nothing has been checked against GOG.** The session's egress proxy denies
`auth.gog.com` (403 on CONNECT), which the smoke test shows as
`request to https://auth.gog.com/token?<redacted> failed: CONNECT proxy failed`.
So this task stays WIP until someone runs it on the mini PC. What that run should
settle, beyond the flow working at all:

1. Whether an unregistered `redirect_uri` (`http://<lan-ip>:<port>/callback`) is
   accepted — if it is, the QR handoff needs no paste at all.
2. Whether any undocumented device-code endpoint exists.
3. Whether the response carries the fields assumed here (`access_token`,
   `refresh_token`, `user_id`, `session_id`, `expires_in`). An unreadable response
   already fails with a clear message rather than a panic.

environment variables.

## 2026-09-17 07:30 — Still the same blocker, now shared

Nothing about the flow has changed. Two things around it have, and both matter to
whoever runs this on the mini PC.

`HttpClient` gained `get_authorized`, so the trait is now "the authorized call is
the one you implement, and plain `get` defaults to it". The auth flow uses `get`
and is unaffected; only the test double in this module changed shape. The reasoning
for that direction is in `RECORD/2026-09-17.library-catalog.WIP.md`.

More importantly, `auth` is no longer the only task waiting on a real network.
`cat` is now in the same state — written, unit-tested, never once checked against
GOG — and `appid` and `vdf` are waiting on a real Steam in the same way. The
checklist in the entry above is therefore a subset of a larger one, and the larger
one is ordered so that a single session at the machine can work through it:

**`RECORD/2026-09-17.mini-pc-verification-plan.WIP.md`**

Use that file rather than this list; the four items above appear in it as step 1,
together with two from the token storage record that belong to the same sitting.
