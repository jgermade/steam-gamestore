# Installing gamestore, and running it from a Steam tile

- **Status:** WIP
- **Started:** 2026-09-17
- **Roadmap:** ROADMAP/2026-09-17/03-platform-linux.md (`appid`, `vdf`),
  ROADMAP/2026-09-17/02-core.md (`auth`)

## 2026-09-17 09:20 — Why this exists

Everything built so far runs out of a checkout with `cargo run`. Nothing installs
it, and nothing puts it in front of Steam, so the four unverified tasks stayed
unverified for want of a way to *start* the program on the machine that could
verify them.

This adds the two missing pieces: a way to install the binary, and a way to put it
in the Steam library as a tile. It deliberately adds no new capability to gamestore
itself — the point is to make the existing code reachable from the target machine,
which is step 1, 3 and 4 of
[`RECORD/2026-09-17.mini-pc-verification-plan.WIP.md`](2026-09-17.mini-pc-verification-plan.WIP.md).

The mini PC runs **CachyOS**: Arch-shaped, mutable, Plasma. That decided the
packaging — a home-directory prefix and a build from source — but nothing here
depends on it, and the same script works on an immutable SteamOS.

## 2026-09-17 09:20 — `install.sh`

Builds `gamestore-cli` with `--locked` and installs the binary to
`~/.local/bin/gamestore`, overridable with `--prefix`. It touches nothing outside
the prefix, so it needs no root and survives an immutable `/usr`. When `cargo` is
missing it says how to get it, naming `pacman -S rustup` when there is a `pacman`.
It ends by running `gamestore info`, so the first thing anyone sees is what
gamestore resolved on that machine rather than a silent success.

## 2026-09-17 09:20 — `gamestore steam-install`

Registers gamestore itself as a non-Steam shortcut, which is the cheapest test of
the two claims this repository cannot check by itself: that `steam::shortcut_appid`
derives the number Steam derives, and that a `shortcuts.vdf` written by
`platform-linux` is one Steam accepts. Installing gamestore *as a game* answers
both within a minute of restarting the client, without a GOG account or a download
existing.

The command prints the appid, the shortcut id and the `compatdata` path it expects,
then names the two things to look at — a `compatdata` directory with a different
number, and a tile that disappears when Steam restarts.

`gamestore steam-uninstall` takes it back out. The appid is derived the same way on
both sides, so removal has to be told the same `--name` and `--no-terminal` the
install was given; the command documents that rather than searching by name.

### The terminal problem

Steam starts a tile with no terminal attached. A command line program launched from
Big Picture therefore draws nothing, exits, and looks broken. The shortcut points at
a small generated launcher (`~/.local/share/gamestore/steam/gamestore-tile.sh`)
which finds a terminal emulator, re-runs itself inside it, and waits for a keypress
at the end so the output can be read. `konsole` is tried first because Plasma is
what CachyOS and SteamOS both ship. `--no-terminal` skips the launcher and points
the tile straight at the binary.

This is a test harness, not the product: `04-ui.md` is where the controller-driven
UI lives, and none of this survives it.

### Two things it refuses to decide

- **Which Steam account.** With one account on the machine the choice makes itself.
  With several, the command errors and lists them, because open question 5 —
  whether a game installed by one user should appear for all of them — is exactly
  what a default here would answer by accident. `--user <id>` or `--all-users`.
- **Whether Steam is running.** It cannot refuse, because the check is advisory, but
  it says so loudly: Steam reads `shortcuts.vdf` at startup and writes it back on
  exit, so a tile added underneath a running client is discarded when that client
  quits. The module documentation in `platform-linux/src/shortcuts.rs` has warned
  about this since it was written; this is the first code to act on it.
  `tile::steam_is_running` matches `/proc/*/comm` exactly against `steam`, so
  `steamwebhelper` — which outlives the client — does not count.

## 2026-09-17 09:20 — What was checked, and what was not

Checked here, against a constructed Steam root: the tile is written into
`shortcuts.vdf`, `userdata/0` is skipped, a second run updates rather than
duplicates, `steam-uninstall` removes it and leaves a file that still parses, two
tiles with different names coexist, and the launcher really does exec the binary.

Not checked, and not checkable here: whether **Steam** agrees. That is the whole
point of the command, and it needs the mini PC.

## 2026-09-17 09:20 — What still blocks the login test

`gamestore login` does not run without GOG OAuth2 client credentials, and nothing
is baked into the binary. That is **open question 3**, and it is now the single
thing between this work and the answer to step 1 of the verification plan. It is a
distribution decision rather than a technical one, so it is left where it was, and
named here so the next run does not rediscover it.

Until it is answered, the credentials come from `config.toml` or from
`GOG_CLIENT_ID` / `GOG_CLIENT_SECRET`, which is enough to test the flow.
