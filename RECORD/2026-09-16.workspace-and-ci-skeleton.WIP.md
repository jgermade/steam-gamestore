## 2026-09-16 23:44 — Workspace skeleton (`ws`)

Created the Cargo workspace the roadmap asks for, with four members and Rust
edition 2024 (`rust-version = "1.85"`):

- `core/` (`gamestore-core`) — `error` (a `thiserror` enum plus a `Result` alias),
  `logging` (a `tracing` subscriber on stderr, filter from `GAMESTORE_LOG`),
  `config` (`Paths` and `Config`), and `platform` (the `Platform` trait).
- `platform-linux/` (`gamestore-platform-linux`) — `LinuxPlatform`, which resolves
  the Steam root from `~/.steam/steam`, `~/.local/share/Steam`, `~/.steam/root`
  and the Flatpak path Bazzite uses, in that order.
- `platform-windows/` (`gamestore-platform-windows`) — `WindowsPlatform`, which
  resolves the Steam root from `%ProgramFiles(x86)%` before `%ProgramFiles%`.
- `cli/` (`gamestore-cli`, binary `gamestore`) — `clap` front end with `info` and
  `config` subcommands.

Decisions worth knowing about:

- **Platform selection is a `cfg`-scoped dependency, not a feature.** `cli`
  declares `gamestore-platform-linux` under
  `[target.'cfg(target_os = "linux")'.dependencies]` and the Windows crate under
  its own target section, so neither platform crate can leak into the other's
  binary. Verified with `cargo tree -p gamestore-cli --target …`: the Windows
  target pulls `core` + `platform-windows`, the Linux target `core` +
  `platform-linux`. `core::platform::UnsupportedPlatform` is the fallback under
  `cfg(not(any(linux, windows)))` so the workspace still builds on macOS instead
  of failing to resolve a dependency.
- **The `Platform` trait stays small** — `id`, `steam_root`, `uses_proton`, and a
  defaulted `default_install_root` — because `01-foundations.md` warns that
  splitting the workspace early can force awkward abstractions. Anything both
  platforms do identically stays in `core`.
- **Directories come from `directories::ProjectDirs`** (XDG on Linux,
  `%APPDATA%` on Windows) and each one can be overridden with
  `GAMESTORE_CONFIG_DIR`, `GAMESTORE_DATA_DIR` or `GAMESTORE_CACHE_DIR`. The
  lookup is injected (`Paths::resolve_with`) so tests never mutate the process
  environment, which `std::env::set_var` makes unsafe in edition 2024 anyway.
- **`Config` uses `serde(default, deny_unknown_fields)`**: a partial file keeps
  the defaults for what it omits, and a typo is an error instead of a silently
  ignored key. Default download concurrency is 4 — polite, since GOG rate-limits.
  `STEAM_ROOT` overrides the Steam lookup on both platforms.
- **No `rust-toolchain.toml`.** Pinning a toolchain would override whatever CI
  installs; the workspace declares `rust-version` instead.

`platform-windows` is deliberately plain path and environment logic with no
Windows API calls, so `cargo build --workspace` is green on Linux too. Reading the
Steam root from the registry belongs to the `wvdf` task; until then `STEAM_ROOT`
covers non-default installations.

Verification on Linux: `cargo fmt --all --check`, `cargo clippy --workspace
--all-targets -- -D warnings` and `cargo test --workspace` (18 tests) all pass,
and `cargo check --workspace --target x86_64-pc-windows-msvc` succeeds, which is
the acceptance criterion of `ws` short of a real Windows runner. `gamestore info`
prints the platform, the resolved paths and, here, `steam root: unavailable` with
the `STEAM_ROOT` hint, since the container has no Steam.
