## 2026-10-06 17:25 — `gamestore install` works end to end

Decided with the owner after the hand-made install
(`RECORD/2026-10-06.manual-install-prototype.completed.md`): reach a playable game
with the offline installer first, and leave the Galaxy content protocol for later.
This runs ahead of a roadmap revision; the revision should record the decision.

Built, one commit per part:

1. `core::installer` — pick the Windows installer, resolve downlinks, parse the
   checksum document, download verified chunk by chunk with resume.
   `http::Fetch` returns the status before the body, because a 200 to a range
   request means the bytes belong at offset 0.
2. `core::text_vdf`, `platform_linux::proton`, `platform_linux::inno` — Steam's
   text VDF, byte-exact on four real files; Proton discovery by internal name and
   directory; the silent install with an absolute path, a display, a throwaway
   prefix and InnoSetup's success line as the evidence.
3. `proton::map` and `core::artwork` — the `CompatToolMapping` writer, and
   SteamGridDB by GOG id with GOG's catalog as a checked fallback.
4. `gamestore install` — the orchestration, with the registry claimed through
   `downloading` and `installing` and marked `installed` or `failed`.

Verified on the mini PC against a sandboxed Steam root (`STEAM_ROOT` pointing at a
copy whose `userdata` and `config` are its own, so the owner's library was not
touched):

- Wolfenstein 3D installed from nothing in about 10 s: a DOSBox game, so the play
  task's arguments (`-conf "..\dosbox_wolf3d.conf" … -c "exit"`) and working
  directory (`DOSBOX`) were exercised. `config.vdf` differed from the real one by
  exactly the new mapping block. Four images, all of the right game.
- Xeno Crisis with its download killed at 52 MiB: the rerun kept the 40 MiB of
  whole verified chunks, fetched the rest by range, and ended on GOG's MD5. The
  existing install was detected and the installer not run again; the appid matched
  the hand-made one.

Detecting a running Steam now asks *which root* it runs from
(`tile::steam_is_running_from`, via `/proc/<pid>/exe`), since only that client
owns the files. That is also what made the sandbox possible.

Not yet: a real run against the live Steam with `--restart-steam`; a multi-part
installer (`.bin` files) end to end; Ludusavi and the `%command%` wrapper;
`uninstall`.

## 2026-10-06 17:50 — First real install, and two things it showed

`gamestore install "Wolfenstein 3D" --restart-steam --all-users` against the live
Steam: tiles in all three accounts, the mapping, four images, Steam stopped and
started through `steam-launcher.service`. It launched from Big Picture under Proton
and Steam created `compatdata/2825521059`, the derived appid, again.

1. **Paths in `goggame-<id>.info` are Windows paths, case included.** It says
   `DOSBOX\dosbox.exe`; the file is `DOSBox.exe`. Wine found it, so the tile works,
   but the stored path did not exist on Linux. `installer::resolve_case` now takes
   each component's on-disk spelling. Because the appid is derived from the exe
   path, this changes the appid such a game gets: rerunning `install` on a game
   installed before this fix adds a second tile rather than updating the first.
   `uninstall`, when it exists, has to find tiles by what it recorded in the
   registry (`steam_appid`), not by re-deriving it.
2. **The controller did not work in Wolfenstein 3D.** Not a gamestore fault: a
   1992 DOS game under DOSBox under Proton only knows a 2-axis joystick or a Gravis
   GamePad, and both are off until enabled in its own Control menu. It is a fair
   warning for the UI phase, though: DOS games from GOG will want a Steam Input
   layout mapping the pad to their keys, and the GOG id plus "runs DOSBox" (visible
   in the play task) is enough to know when to offer one.

## 2026-10-06 18:00 — Do not stop Steam under a running game, and what that means for the UI

`--restart-steam` would have closed whatever game was being played when the
install reached its last step. `tile::steam_game_running` finds a game through
Steam's `reaper` process (`SteamLaunch AppId=<appid>`), and `install` now stops
there with everything before the Steam writes kept, so a rerun only writes them.

The owner asked to install from the gamestore tile rather than a shell. Not
possible as things stand, and the reason is a constraint the UI phase has to
design around: anything launched from Steam is itself under `reaper`, and stopping
Steam to write `shortcuts.vdf` and `config.vdf` stops it too. The tile can
download and install, but the Steam writes have to happen outside Steam's
lifetime — queued and applied by something that outlives the client (a user
systemd unit run after `steam-launcher.service` stops, or at the next session
start), with the registry saying "waiting for Steam to restart" in the meantime.
That belongs in the next roadmap revision, under `04-ui.md` and `compat`.

## 2026-10-08: depth16 checks the switch and retries

Moto Racer stopped again at "16 bit screen mode required" (data/delphine.err), with
nothing changed since it last worked. Traced with WINEDEBUG=+system: depth16's
ChangeDisplaySettingsA can run before Wine's desktop has its display ready
("find_source_by_index Failed to find source with id 1" in depth16's own thread),
fail, and depth16 started the game anyway, at 32 bits. It now checks the return
value and that the current mode reads 16 bits, retrying every 250 ms for up to
10 s before starting the game. Two back-to-back runs on the mini PC: the second
needed the retry (two ChangeDisplaySettings calls) and the game started.

The earlier guess that the in-game 16:9 option lives in data/bestscor.dat was
wrong: the current file, the copy kept as bestscor.dat.16-9 and the installer's
are byte-identical.

## 2026-10-08: Moto Racer without dgVoodoo

The retry above was not the whole story. With a Proton log from a Steam launch
(user_settings.py in the Proton directory, removed afterwards): depth16 sets
1920×1080 at 16 bits and the game sees 16 bits; then game.EXE, through
dgVoodoo's D3D11 output and DXVK's DXGI, sets 1920×1080 at 32 bits with
CDS_FULLSCREEN, Wine re-reads the display ("add_modes current ... 32bits"), and
the game's next depth check fails. It worked on 2026-10-06 because the check came
first; with warm caches it now never does. Tried, all failing on the TV:
FullscreenAttributes = fake, windowed with borderless,fullscreensize (the 32-bit
change still happens), depth16 watching and setting 16 bits back while the game
runs (the dialog's Retry then exits; Ignore just asks again), and
DesktopBitDepth = 16 (page fault inside dgVoodoo's DDraw, 2.87.5).

Without dgVoodoo's DLLs the game asks for 640×480 at 16 bits itself and starts
every time. The fix drops dgVoodoo and its ddraw/d3dimm overrides; on the mini PC
the DLLs were moved to dgvoodoo-desactivado/ in the game directory, which needed
no Steam restart since ddraw=n,b falls back to Wine's own.

Also tried, at the user's suggestion: a Wine virtual desktop (HKCU\Software\Wine\Explorer
Desktop=Default, Desktops\Default=1920x1080) with dgVoodoo. Worse: dgVoodoo's
DirectDrawCreate fails inside it ("Fatal error in Cdd createDD ... 0x80004005").
Undone; without dgVoodoo the game starts as before.

Patching the check, at the user's suggestion: game.EXE (GOG, sha256 b2f921098f9ba59b…)
reads the desktop depth with IDirectDraw::GetDisplayMode at 0x45a6a6 and at
0x45a7c2 does `cmp eax,0x10; je 0x45a8bc`, else shows the Abort/Retry/Ignore box
(MessageBoxA, 0x40112; the text is message 0xB1 of its 7-field table). Making it
`jmp 0x45a8bc` (file offset 0x59bc9: 0f84ed000000 -> e9ee00000090) gets past the
check, and then dgVoodoo 2.87.5 crashes creating the first 640×480 surface
(page fault at ddraw+0xaf4a, called from game+0x75e0a), the same crash as with
DesktopBitDepth = 16. So the check was only the first symptom: dgVoodoo fails to
start this game whenever the desktop is 32-bit at that point, which is now every
time. Reverted to the original game.EXE without dgVoodoo (kept under
dgvoodoo-desactivado/ with the DLLs); the game starts.

Windowed, at the user's suggestion: game.EXE without -fullscreen, dgVoodoo with
FullScreenMode = false and WindowedAttributes = borderless,fullscreensize, then also
Resolution = unforced. The game still sets 1920×1080 at 32 bits right after start
and dgVoodoo crashes at the same ddraw+0xaf48. (Earlier tests outside Steam passed
the launcher's Params as one argument, since zsh does not split $P; these used
${=P}.) Back to no dgVoodoo.
