## 2026-10-06 17:25 — `gamestore install` works end to end

Decided with the owner after the hand-made install
(`RECORD/2026-10-06.manual-install-prototype.completed.md`): reach a playable game
with the offline installer first, and leave the Galaxy content protocol for later.
This runs ahead of a roadmap revision; the revision should record the decision.

Built, one commit per part:

1. `core::installer` — pick the Windows installer, resolve downlinks, parse the
   checksum document, download verified chunk by chunk with resume.
   `http::Fetch` returns the status before the body, because a 200 to a range
   request means the bytes belong at offset 0.
2. `core::text_vdf`, `platform_linux::proton`, `platform_linux::inno` — Steam's
   text VDF, byte-exact on four real files; Proton discovery by internal name and
   directory; the silent install with an absolute path, a display, a throwaway
   prefix and InnoSetup's success line as the evidence.
3. `proton::map` and `core::artwork` — the `CompatToolMapping` writer, and
   SteamGridDB by GOG id with GOG's catalog as a checked fallback.
4. `gamestore install` — the orchestration, with the registry claimed through
   `downloading` and `installing` and marked `installed` or `failed`.

Verified on the mini PC against a sandboxed Steam root (`STEAM_ROOT` pointing at a
copy whose `userdata` and `config` are its own, so the owner's library was not
touched):

- Wolfenstein 3D installed from nothing in about 10 s: a DOSBox game, so the play
  task's arguments (`-conf "..\dosbox_wolf3d.conf" … -c "exit"`) and working
  directory (`DOSBOX`) were exercised. `config.vdf` differed from the real one by
  exactly the new mapping block. Four images, all of the right game.
- Xeno Crisis with its download killed at 52 MiB: the rerun kept the 40 MiB of
  whole verified chunks, fetched the rest by range, and ended on GOG's MD5. The
  existing install was detected and the installer not run again; the appid matched
  the hand-made one.

Detecting a running Steam now asks *which root* it runs from
(`tile::steam_is_running_from`, via `/proc/<pid>/exe`), since only that client
owns the files. That is also what made the sandbox possible.

Not yet: a real run against the live Steam with `--restart-steam`; a multi-part
installer (`.bin` files) end to end; Ludusavi and the `%command%` wrapper;
`uninstall`.

## 2026-10-06 17:50 — First real install, and two things it showed

`gamestore install "Wolfenstein 3D" --restart-steam --all-users` against the live
Steam: tiles in all three accounts, the mapping, four images, Steam stopped and
started through `steam-launcher.service`. It launched from Big Picture under Proton
and Steam created `compatdata/2825521059`, the derived appid, again.

1. **Paths in `goggame-<id>.info` are Windows paths, case included.** It says
   `DOSBOX\dosbox.exe`; the file is `DOSBox.exe`. Wine found it, so the tile works,
   but the stored path did not exist on Linux. `installer::resolve_case` now takes
   each component's on-disk spelling. Because the appid is derived from the exe
   path, this changes the appid such a game gets: rerunning `install` on a game
   installed before this fix adds a second tile rather than updating the first.
   `uninstall`, when it exists, has to find tiles by what it recorded in the
   registry (`steam_appid`), not by re-deriving it.
2. **The controller did not work in Wolfenstein 3D.** Not a gamestore fault: a
   1992 DOS game under DOSBox under Proton only knows a 2-axis joystick or a Gravis
   GamePad, and both are off until enabled in its own Control menu. It is a fair
   warning for the UI phase, though: DOS games from GOG will want a Steam Input
   layout mapping the pad to their keys, and the GOG id plus "runs DOSBox" (visible
   in the play task) is enough to know when to offer one.
