# GOG login flow: manual code paste first, QR handoff as a nice to have

- **Status:** completed (decision recorded; implementation belongs to `auth`)
- **Started:** 2026-09-16
- **Roadmap:** ROADMAP/2026-09-16/02-core.md (`auth`), and open question 3 in
  ROADMAP/2026-09-16/08-open-questions.md

## 2026-09-16 23:58 — Decision

The question was whether the GOG login could be completed from a phone by
scanning a QR code on the TV, since the mini PC runs in console mode with only a
controller.

**Decision: `auth` ships the manual code paste as its primary flow. The
QR-assisted handoff is a nice to have, added later, not a prerequisite for M1.**

### What GOG offers

- **No device authorization grant.** GOG publishes no RFC 8628 `device_code`
  endpoint, so the flow that would make a QR trivial (show code, poll for the
  token) does not exist.
- **No client registration.** Every open-source client (Heroic/`gogdl`,
  `lgogdownloader`, GameHub) uses the well-known GOG Galaxy client credentials,
  and that client's `redirect_uri` is fixed to
  `https://embed.gog.com/on_login_success`. None of them capture the
  authorization code automatically: they all end with the user copying the final
  URL. This ties directly into open question 3.
- Consequence: a custom backend does not help here either. It cannot be the
  redirect target, so there is nothing for it to relay.

### The QR flow, for when it is built

1. The binary serves a local HTTP endpoint on the LAN with a single-use random
   path and a short TTL (about five minutes).
2. The TV shows a QR for `http://<lan-ip>:<port>/pair/<token>`.
3. The phone opens it, follows the GOG authorization URL, and logs in — captcha
   and two-factor included, which is precisely what is painful with a gamepad.
4. GOG lands the phone on `embed.gog.com/on_login_success?...&code=…`. The user
   pastes that address (or the bare code) into the page from step 2.
5. The code→token exchange still runs in the binary on the mini PC, so the client
   secret never leaves it.

It removes the typing, not the paste. That is why it is an improvement on the
manual flow rather than a different flow, and why the manual flow has to work
first: the same code extraction and the same token exchange serve both.

Security notes for whoever implements it: bind to the LAN interface only,
single-use token with a TTL, never log the code or the tokens (`tok` already
requires the latter), and accept that a plain-HTTP LAN hop carries a short-lived
single-use code.

### Two checks `auth` should run first

Neither could be verified from the session where this was written: the egress
proxy denies `auth.gog.com` (403 on CONNECT). Both are cheap to run on a real
machine and one of them would change the design:

1. **Does `auth.gog.com` accept an unregistered `redirect_uri`,** for example
   `http://<lan-ip>:<port>/callback`? Exact-match against a registered URI is the
   norm, so this is expected to fail — but if it succeeds, the phone delivers the
   code straight to the mini PC and the QR flow needs no paste at all.
2. **Is there any undocumented device-code endpoint?** Same reasoning: if one
   exists, the QR becomes the natural primary flow instead of a nice to have.

If check 1 fails, the `auth` bullet about a *"local redirect capture: a loopback
listener"* is not viable with the Galaxy client credentials — the redirect goes to
`embed.gog.com`, never back to us — and the manual paste is not a fallback but the
only path. `auth` should settle this before writing the flow.

### Roadmap handling

`ROADMAP/2026-09-16/` is historical and stays as it is. The QR handoff and the
outcome of the two checks belong in the next roadmap revision, as a nice-to-have
task after `auth` rather than inside it.
