# Controller UI: cover grid, search with an on-screen keyboard, install and uninstall

- **Status:** completed (requirement and design recorded; implementation is a new
  roadmap phase)
- **Started:** 2026-09-16
- **Roadmap:** answers open question 4 in
  ROADMAP/2026-09-16/08-open-questions.md; touches `feed` in
  ROADMAP/2026-09-16/04-saves.md

## 2026-09-16 23:59 — Requirement

The tile in the Steam library should open a controller-driven UI, not just a CLI:

- A **grid of game covers** for the GOG library.
- A **search box with an on-screen keyboard**, usable with a gamepad alone.
- **Install and uninstall** actions per game.

This settles open question 4 ("How are games added — from a tile, or only from the
CLI?") in favour of a UI. The CLI stays: it is what makes the flow testable
without a display, and `cli` remains the entry point that the Steam shortcut
launches.

## Design decisions

### A separate `ui` crate, and one UI binary for everything

The UI goes in its own workspace member, so `core` stays headless and the CLI
keeps working on a machine with no display — the same split phase 0 set up. The
pre/post launch screens from `feed` become **modes of this same UI**, not a second
toolkit: `04-saves.md` ruled out a `wlr-layer-shell` HUD, and a fullscreen window
before and after the game is what this UI already draws.

### Toolkit: `egui` via `eframe`

Recommended over the alternatives considered:

- **`egui`/`eframe`** — immediate mode, so a focus-navigated grid is a few lines
  of state rather than a widget tree with focus plumbing; renders fullscreen as an
  ordinary Wayland client under gamescope; works unchanged on Windows for M5;
  no browser, no HTML. Note `eframe` 0.36 requires Rust 1.95, so pin 0.35 while
  the workspace declares `rust-version = "1.85"`, or raise that floor
  deliberately.
- **`slint`** — nicer for a designer-authored look, heavier to wire.
- **A local web UI in a kiosk browser** — rejected: it drags a browser into the
  dependency set for a two-screen application.

### Gamepad input and the on-screen keyboard are ours

- Steam's on-screen keyboard belongs to Steam's own UI and the overlay; relying on
  it for our window under gamescope is not something to build on. **We draw our
  own OSK**: a grid layout with A to type, B to close, X backspace, Y shift,
  shoulder buttons to move the caret. A real keyboard must keep working too, since
  that is how it gets tested.
- Gamepad events come from **`gilrs`** (evdev, no SDL dependency), mapped to focus
  movement in the grid. Keyboard and gamepad feed the same navigation state.

### Covers

- Use the artwork GOG already serves with the catalog, cached under
  `Paths::cache_dir`, so browsing works with the network down — `cat` already
  requires a local catalog cache for that reason. SteamGridDB is a later
  fallback for missing art and would need an API key, so it is not a dependency
  of the first version.
- Fetch art when the catalog is refreshed, not when the grid is drawn: a grid that
  blocks on the network is worse than a grid with placeholders.

### Uninstall

Uninstall removes, in this order: the Steam shortcut (the `vdf` writer is
idempotent, so removal is the same code path), the Proton prefix under
`compatdata/<appid>`, the generated launch wrapper, and the installed files.

**It never deletes saves.** Ludusavi's backups are the undo path for everything
else in this project (`05-save-sync.md` says not to prune them aggressively), and
a controller-driven UI on a machine shared with the kids is exactly where a
mis-click must not be destructive. Uninstall asks for confirmation; deleting
backups is not an option it offers.

## What this implies for the plan

- The UI depends on `cat` for the grid, and on `dl`/`inno`/`vdf` for install and
  uninstall, so the full version lands after M2. What should come **early** is a
  spike: draw the grid and the OSK with fake data under gamescope and drive it
  with a controller. That de-risks the three things that cannot be checked from a
  desktop — gamescope focus, gamepad mapping, and legibility on a TV — before any
  of it is wired to real data.
- `ROADMAP/2026-09-16/` stays as it is, per `AGENTS.md`. This needs a **new dated
  roadmap revision** with a UI phase, the spike scheduled early, `feed` folded
  into the UI, and open question 4 moved out of the open list.
- The QR login handoff recorded in
  `RECORD/2026-09-16.gog-login-flow-decision.completed.md` becomes cheaper once
  this UI exists: the QR is just another screen, and the paste step stays on the
  phone.

## 2026-09-17 00:05 — Grid state: installed badge and install progress

Added to the requirement: each cover in the grid carries a **badge saying whether
the game is installed**, and while it is being installed a **progress bar along
the bottom edge of the cover**.

Design notes that follow from it:

- **The grid needs a per-game state, and it has to be persisted.** A badge cannot
  be derived from the catalog, which only says what is owned. The installed-games
  registry under `Paths::data_dir` becomes the source of truth for the badge, for
  uninstall, and for the launch wrapper; the catalog cache stays a cache. States
  worth distinguishing: not installed, queued, downloading, installing, installed,
  update available, failed.
- **The progress bar covers two phases with very different granularity.** `dl`
  reports bytes and already exposes "progress reporting through a channel, so the
  CLI and any UI can subscribe" (`02-core.md`) — that channel is what the bar
  subscribes to. The silent InnoSetup step (`inno`) reports nothing useful, so the
  bar is determinate while downloading and indeterminate while installing, with
  the phase named next to it. Faking a percentage for the install phase is worse
  than showing that it is working.
- **Failed is a state the badge must show**, not a dialog that has been dismissed
  and lost. `inno` has to surface installers that ignore the silent flags, and in
  Big Picture there is no terminal to read the error from; the tile is where it has
  to be visible, with the per-game log path available from the detail view.
- The bar draws over the cover's bottom edge, so it must stay legible over arbitrary
  artwork: a solid track behind it rather than alpha over the image.
- This is also what makes the UI usable while something installs: the grid stays
  navigable, one game installs in the background, and the badge is how the state
  comes back after the UI is closed and reopened.

Both items belong to the same UI phase as the rest, and the early spike should
already draw a badge and a fake progress bar — they are the two things most likely
to be illegible on a TV from a sofa.
