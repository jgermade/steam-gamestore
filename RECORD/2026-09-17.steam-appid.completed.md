# Non-Steam appid derivation (CRC32)

- **Status:** completed
- **Started:** 2026-09-17
- **Roadmap:** ROADMAP/2026-09-17/03-platform-linux.md (`appid`)

## 2026-09-17 07:05 — The derivation, and the one thing it cannot prove

`core::steam` derives the identifier Steam gives a non-Steam shortcut:

- `crc32` — table-driven CRC-32 (IEEE, reflected `0xEDB88320`), the same function
  `zlib.crc32` computes.
- `shortcut_appid(exe, app_name)` — `crc32(exe ++ app_name) | 0x80000000`. This is
  the number that names the Proton prefix (`compatdata/<appid>`) and the artwork.
- `shortcut_id` / `appid_to_shortcut_id` / `shortcut_id_to_appid` — the 64-bit form,
  `(appid << 32) | 0x02000000`, and the conversions both ways.
- `quote_exe` — the executable as Steam stores it, quoted.
- `compatdata_name` — the prefix directory name.

### It is in `core`, not `platform-linux`

The roadmap schedules `appid` in the Linux phase, and this does not follow it. The
derivation is arithmetic over two strings with nothing platform-specific in it, and
`wvdf` in the Windows phase needs the identical function; `AGENTS.md` says what both
platforms do the same way belongs in `core`. Putting it in `platform-linux` would
buy a move later and a duplicate in the meantime. The scheduling is unaffected —
this is about which crate, not which phase.

### Quoting is the trap, so the API makes it hard to get wrong

The CRC is over **the string stored in the shortcut's `Exe` field**, and Steam
stores that quoted. So `/games/game.exe` and `"/games/game.exe"` are two different
shortcuts as far as the appid is concerned, and picking the wrong one does not fail
loudly — it produces a valid-looking appid naming a prefix Steam never launches
into. That is the appid-mismatch risk `03-platform-linux.md` flags. `quote_exe`
lives next to `shortcut_appid` for that reason, the doc comments on both say the
same string must go into the appid and into the VDF, and there is a test asserting
the two spellings differ, so nobody "simplifies" the quotes away.

### Verification

Nine tests. The CRC half is pinned by sixteen vectors **generated from Python's
`zlib.crc32`**, an implementation with no shared ancestry with this one, and they
include the cases most likely to diverge: non-ASCII titles (`Brütal Legend`,
`日本語のタイトル`), an apostrophe, a Windows path with backslashes, and a quoted
exe concatenated with a name. A separate test asserts the CRC is over UTF-8 bytes
rather than characters, since a library full of accented titles is the normal case,
not the edge one. The rest cover the high bit, determinism, sensitivity to both
inputs, the two id widths converting both ways, and that the appid is formatted as
a large unsigned number rather than a negative one.

One of those vectors was wrong on the first attempt — `message digest` was written
from memory as `0x203839c3` when it is `0x20159d7f` — and the test caught it. The
implementation was right; the constant was not. Worth recording because it is the
argument for generating vectors from an independent implementation rather than
recalling them.

**What none of this proves is the Steam-specific half.** The tests pin that the
checksum is a real CRC-32 and that the composition is self-consistent, but *which
string Steam feeds in* and *which mask it applies* are assumptions taken from
reference implementations, and no test here can check them. Only Steam can. So:

`gamestore appid --exe <path> --name <name>` prints the stored spelling, the appid,
the 64-bit id and the `compatdata` path. On the mini PC, add a non-Steam shortcut by
hand, then compare: if the printed appid names the `compatdata` directory Steam
created, the derivation is right. The roadmap says to test this end to end early and
this command is what makes "early" cheap.

The artwork line that command prints is deliberately hedged. Which appid variant the
files under `config/grid/` use is itself an open question in
`RECORD/2026-09-17.pending-roadmap-changes.WIP.md`, so it is offered as the thing to
check rather than stated as the answer.
