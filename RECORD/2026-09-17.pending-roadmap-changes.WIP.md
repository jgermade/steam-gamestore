## 2026-09-17 01:15 — Why this file exists

Decisions are recorded as they are made, but a roadmap revision is a dated
snapshot: per `AGENTS.md` its task states are only refreshed when a newer revision
is drafted, and existing dated directories are never rewritten. So between
revisions the plan and the decisions drift apart on purpose.

Rather than draft a revision per decision, decisions accumulate and the next
revision folds them in together — most likely once `auth` is closed with a run on
the mini PC, since that run answers several open questions at once.

This file is the accumulator: **one entry per decision that the next revision has
to absorb**, appended as they land. When that revision is drafted, it is renamed to
`.completed.md` and the new revision's own record takes over.

- **The Gantt is now wrong about the shape of the work, not just its state.**
  `appid`, `vdf` and `state` are done and `cat` is written-but-unverified, yet the
  chart has `appid` starting after `cat` and the whole Linux phase opening on
  2026-10-05. In practice the deterministic, offline-verifiable tasks ran first
  precisely *because* they do not depend on GOG. The next revision should order the
  early chart by what each task depends on being verified, not only by what it
  depends on being written.
- `02-core.md`, `cat`: done except verification, same state `auth` is in. Both are
  waiting on the same thing.
- `02-core.md`, `state`: done. Worth noting in the task text that "resumable" splits
  in two — the registry half is done, the resume-the-bytes half belongs to `dl`/`ver`.
- `03-platform-linux.md`, `appid` and `vdf`: done, and **they live in `core`**, not
  `platform-linux`. `appid` is arithmetic both platforms share; the VDF codec and the
  typed shortcut layer are a file format, not a platform. What stayed in
  `platform-linux` is Steam's directory layout. Open question 2 asked where the
  writer should live and its answer is: the codec in `core`, the layout per platform.
  The next revision should move that question to the settled list.
- `03-platform-linux.md`, `compat`: detecting a running Steam is scheduled there, but
  it is `vdf` that needs it first — a shortcut written under a running client is
  discarded when that client exits, which is the most likely way a user's first
  install appears to do nothing. Consider pulling the detection earlier, or making
  it its own small task before `compat`.
- `10-open-questions.md`, question 5 (multi-user Steam): now blocking in practice.
  `steam_users` returns every account and something has to choose. It cannot be
  settled by code.
- **A new nice-to-have, from three uses:** rewriting `#[cfg(unix)]`/`#[cfg(target_os)]`
  gates to compile the other branch on Linux is how the Windows and non-Linux paths
  get checked without the MSVC toolchain, and it has caught one real `-D warnings`
  failure. It is currently a technique written down in records. It should be a script
  in the repository and a CI job, or it will be forgotten.
