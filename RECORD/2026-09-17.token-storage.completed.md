# Token storage and refresh

- **Status:** WIP
- **Started:** 2026-09-17
- **Roadmap:** ROADMAP/2026-09-17/02-core.md (`tok`)

## 2026-09-17 01:40 — Keyring store and session, minus the no-keyring path

`core::tokens` adds:

- **`TokenStore`** — a trait (`load`, `save`, `clear`, `describe`), so the session
  does not care where tokens live and the tests do not need a keyring.
- **`KeyringStore`** — the platform keyring: Secret Service on Linux, the credential
  manager on Windows, one entry per account name so two Steam users on the same
  machine can keep separate GOG sessions. `TokenSet` is stored as JSON, which is why
  it gained `Serialize`/`Deserialize` while keeping its redacting `Debug`.
- **`MemoryStore`** — keeps the session for the lifetime of the process. For tests,
  and for a run that deliberately stores nothing.
- **`Session`** — `restore`, `log_in`, `log_out`, `access_token`. It refreshes when
  the token is within the one minute margin and **stores the rotated refresh token**;
  GOG rotates it, so keeping the old one would break the next refresh. There is a
  test asserting exactly that, because it is the kind of thing that works for an hour
  and then stops.

Two failure modes are handled differently on purpose:

- **The refresh token is revoked or invalid** (`invalid_grant`): the stored session
  is useless, so it is discarded and the error says to run `gamestore login` again.
  Keeping it would only make the next run fail identically.
- **The refresh failed for any other reason** (no network, GOG down): the session is
  kept. A flaky network must not log the user out, and there is a test for that too.

`cli` now stores what it obtains: `login` persists the session and reports where,
`logout` forgets it, and `info` gained a `gog session:` line.

### keyring 4 needs its default store, and hides why it has none

`keyring::Entry::new` returns `NoDefaultStore` whose message is "No default store
has been set, so cannot search or create entries" — which says nothing useful. The
reason lives in `keyring::Entry::store_status()`, so `keyring_error` now appends it.
In this container the message becomes:

```
the platform keyring is not usable: No default store has been set, so cannot search
or create entries (Platform failure: no secret service provider or dbus session found)
```

That is exactly the state a machine booted straight into gamescope is likely to be
in, which makes the next decision the important one.

### Open decision: what happens with no keyring

`02-core.md` says "encrypted file fallback", and it deserves a second look before
being built, because on this machine the fallback is likely to be the *normal* path,
not the exception:

1. **Keyring only.** Honest, and possibly unusable on the target machine.
2. **Encrypted file.** The key has to live somewhere the same machine can read
   unattended, so it is obfuscation, not secrecy. It reads as more protection than
   it gives.
3. **Plain file with `0600`, stated plainly.** Same real protection as 2 against
   anything short of another local user reading the file, without pretending.

Not decided here; the `tok` task stays open until it is.

### Verification

43 tests pass on Linux, covering the store round trip, a valid token not being
refreshed, refresh with rotation persisted, a revoked refresh discarding the
session, a transport failure keeping it, and logout clearing both.

Two things this session cannot exercise: the keyring itself (no D-Bus session) and
anything over the network (the proxy denies `auth.gog.com`).

A note for later: writing the first version of these tests, three of them failed
because `auth::exchange_code` stamps expiry from the real clock while the tests drove
a fake one from the Unix epoch. The fix was to seed the store rather than log in.
If a test ever needs a login on a fake clock, the exchange needs an injectable clock
the way `access_token_at` has one.

Also worth recording: **the workspace can no longer be cross-checked for Windows
from a Linux session.** `ureq` pulls `rustls` and therefore `ring`, whose build needs
MSVC's `lib.exe`; `cargo check --target x86_64-pc-windows-msvc` now fails in the
container with `failed to find tool "lib.exe"`. The `windows-latest` job in CI is the
real check for that target, and it builds the whole workspace, so nothing is lost
except the local shortcut.

## 2026-09-17 06:16 — Decided: a plain `0600` file, said out loud

The open decision above is settled in favour of option 3, the plain file. Option 2,
the encrypted file that `02-core.md` asked for, is rejected: the key has to live
where the same machine can read it unattended, so it is obfuscation wearing the
costume of secrecy, and the costume is the problem — someone reading "encrypted"
in the README would reasonably store their credentials differently than someone
reading "a file only your user can read". Option 1 was never really available: a
box booted straight into gamescope has no D-Bus session, so keyring-only means
login-fails-only on the exact machine this is for.

So `core::tokens` gains:

- **`FileStore`** — `TokenSet` as JSON under `Paths::data_dir/sessions/<account>.json`.
  Written by rename over a temporary, because the machine is a console that gets
  switched off at the wall and a half-written session is worse than no session. The
  file is created `0600` and its directory `0700`; both are set explicitly after
  creation as well as through `OpenOptions::mode`, since `mode` only applies when
  the file is created and a temporary left by a previous crash would otherwise keep
  whatever permissions it had. There is a test for exactly that, seeding a `0644`
  leftover and asserting what survives.
- **`open_store`** — keyring first, file second, returning an `OpenedStore` that
  carries *why* the keyring was not used. Probing is `load()`, not `Entry::new`:
  `Entry::new` can succeed on a machine whose first read then fails, and a read
  that finds nothing is the healthy empty case.
- **`TokenStore for Box<dyn TokenStore>`** — the backend is now a run-time choice,
  and this keeps `Session` generic without making every caller generic.
- **`account_from_env`** / `GAMESTORE_ACCOUNT` — this closes the fourth `tok`
  checkbox. The data directory override already separates two Steam users' files;
  what it cannot separate is keyring entries, which are per-machine, so the account
  name does that. Account names reach the filesystem, so `file_name` reduces them to
  `[A-Za-z0-9_-]` and there is a test that `../../etc/passwd` stays in the sessions
  directory.

The loudness is the point of the decision, so it is not left to the README:
`gamestore info` prints a `gog tokens:` line with the path and the word
`unencrypted`, and the keyring's own reason underneath it; `login` adds "Anyone who
can read that file can use the session." A test pins the pair together — if
`keyring_unavailable` is set the description must start with `file (`, and
otherwise with `platform keyring` — because that pair is the whole user-facing
claim and the two could drift apart silently.

### Verification

43 tests in `core` (was 33), 53 in the workspace; `cargo fmt --all --check` and
`cargo clippy --workspace --all-targets -- -D warnings` are clean. Ten are new:
the file round trip through a directory that did not exist, clear-and-clear-again,
a corrupt file reporting "log in again" rather than panicking, the `0600`/`0700`
modes, the `0644` leftover, two accounts not colliding, a hostile account name not
escaping, `describe` naming the file and saying `unencrypted`, a refresh rotating
through a boxed store into the file, and the `open_store` consistency check.

By hand in this container, which has no Secret Service and so takes the fallback on
every command: `info` with nothing stored, `info` with a session seeded into the
file, `logout` removing it, and `GAMESTORE_ACCOUNT=player-two` resolving to a
different file. `login` itself still cannot be run here — the proxy denies
`auth.gog.com`.

### What this does not settle

`tok` is closed, but the *storage* it exercises is still only ever holding tokens
this repository's tests made up. The first real end-to-end proof comes with the
`auth` run on the mini PC, and one thing to watch there: whether GOG's `expires_in`
and the rotation behave as the round trip assumes over a session long enough to
refresh more than once.

The file is renamed to `.completed.md` with this entry. The `Status:` line at the
top still reads `WIP` because the header is a line already written and records are
append-only; the file name is what carries the status, the same way
`RECORD/2026-09-16.workspace-and-ci-skeleton.completed.md` does.

## 2026-09-17 06:30 — The Windows branch can be checked locally after all

The previous record said the workspace can no longer be cross-checked for Windows
from a Linux session, because `ureq` pulls `ring`, whose build wants MSVC's
`lib.exe`. That is still true of `--target x86_64-pc-windows-msvc`, but it is not
the only question worth answering: this change adds `#[cfg(unix)]` blocks, and what
actually needed checking was whether the *other* branch of those blocks compiles.

That can be done on Linux without the Windows target at all — rewrite the gates so
the non-unix branch is the one selected here:

```sh
sed -i 's/#\[cfg(not(unix))\]/@@P@@/; s/#\[cfg(unix)\]/#[cfg(windows)]/; s/@@P@@/#[cfg(not(windows))]/' \
  core/src/tokens.rs
cargo clippy -p gamestore-core --all-targets -- -D warnings && cargo test -p gamestore-core
```

`windows` is false on Linux and `not(windows)` is true, so exactly the code Windows
CI compiles is compiled, with cfgs clippy treats as ordinary — an earlier attempt
using `#[cfg(all())]` failed on `clippy::non_minimal_cfg`, which is a complaint
about the trick rather than about the code. Clean under `-D warnings`, and the 41
tests that are not `#[cfg(unix)]` pass. Restore the file afterwards; this is a
throwaway edit, not something to commit.

What it does not cover is behaviour: `std::fs::rename` replacing an existing file
is a documented guarantee on Windows (`MoveFileEx` with `MOVEFILE_REPLACE_EXISTING`)
rather than something proven here, and the credential manager is still only
exercised by the `windows-latest` CI job.
