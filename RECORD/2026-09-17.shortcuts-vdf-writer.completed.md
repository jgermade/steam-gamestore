- **Status:** completed

## 2026-09-17 07:55 — Three layers, and one property that matters more than the rest

`shortcuts.vdf` is not ours. Steam writes it, and so do Boilr, Heroic and whatever
else the user installed. The failure mode to design against is not "our shortcut is
wrong" — that is visible and fixable — but "our write silently deleted somebody
else's games", which is discovered weeks later with no way back. So the work is
split so that the not-losing-anything part is testable on its own:

- **`core::vdf`** — the binary format. A `Value` tree (`Map`/`String`/`Int32`/
  `UInt64`) that keeps **every key, in file order, with its original type**, and a
  writer that puts the bytes back exactly as they came in. The load-bearing test is
  `a_document_round_trips_byte_for_byte`: parse a document and re-serialize it, and
  not one byte may differ.
- **`core::shortcuts`** — the typed view. `upsert` writes only the fields gamestore
  owns onto whatever entry is already there, so a tag the user added in Big Picture
  or a `LaunchOptions` they edited by hand survives a reinstall. `remove` is keyed
  on the appid, which is what `uninst` will have in the registry.
- **`platform-linux::shortcuts`** — Steam's layout. Which users exist, where their
  file is, the backup, and the atomic replace.

### What the parser refuses to do

Three cases where guessing would corrupt the file, and the code stops instead:

- **An unknown type tag.** Binary VDF has types this does not implement (`0x03` is
  a float). Skipping one means not knowing its width, which desynchronises the
  parse and turns every later entry into garbage. The error names the byte.
- **Invalid UTF-8 in a string.** A lossy conversion would write the replacement
  character back into someone else's entry. Refusing means gamestore will not touch
  that file, which is recoverable; corrupting it is not.
- **Trailing bytes**, and a NUL inside a value on write, which would silently
  truncate the field when Steam read it back.

Refusing is the right answer to all three because the user is never stuck: the file
is Steam's, the backup exists, and nothing has been changed.

### Two details that are quiet bugs if you miss them

**Case.** Steam has shipped both `AppName` and `appname`, and third-party tools
picked different spellings. A case-sensitive lookup finds nothing on somebody else's
file, so an existing shortcut reads as absent and gets added a second time. Lookups
ignore case, and `set` keeps the spelling already in the file rather than imposing
ours.

**Renumbering.** The entries are keyed `"0"`, `"1"`, `"2"`. Steam stops reading at
the first gap, so removing entry 1 without renumbering does not remove one game — it
hides every game after it. `remove` renumbers, and there is a test for the indices
being contiguous.

### The backup is taken once, deliberately

`save` copies the file before the first write and never overwrites that copy. If it
backed up on every write, the first buggy write would launder itself into the only
surviving copy on the second. The backup's job is the file as it was *before
gamestore ever touched it*.

### Also here: `core::atomic`

The token store's atomic write was pulled out and shared, since the registry
(`state`) and this both need it. `Access::Private` keeps the `0600`/`0700` behaviour
the session file needs; `Access::Default` leaves the umask alone, because Steam's
`config/` is not ours to tighten — there is a test asserting we do not. The
temporary file is written *beside* the target rather than in the system temporary
directory: a rename is only atomic within one filesystem.

### Verification

99 tests in the workspace (was 63): 11 for the codec, 12 for the typed layer, 5 for
the atomic write, 9 new on the Linux side. The ones worth naming:

- a document round-tripping byte for byte;
- a foreign entry, carrying a `UInt64` field we do not manage and a user's tag,
  surviving adding *and* removing one of ours — asserted by comparing the file
  bytes before and after, so anything lost anywhere shows up;
- upserting twice producing identical bytes, which is the idempotence `uninst` and
  reinstall both rely on;
- every prefix of a valid document failing to parse rather than panicking;
- the first save preserving the original while later ones leave the backup alone.

**The Windows branch check from the last record earned its keep.** Running it on
`core::atomic` found `create_dir`'s `access` parameter unused off unix, which is an
`unused_variable` and therefore a failed `-D warnings` build on the `windows-latest`
job — a red CI that would have cost a cycle to discover. Fixed before pushing. Worth
repeating: the technique is cheap and it has now caught something both times it has
been run.

### Not done here, and deliberately

- **Detecting a running Steam.** Steam reads this file at startup and writes it
  back on exit, so a change made underneath a running client is discarded when it
  quits. `03-platform-linux.md` schedules the detection under `compat`; until then
  the module documentation says a write only sticks while Steam is stopped, and the
  UI will have to surface it. This is the most likely way a user's first attempt
  appears to do nothing.
- **Choosing which user to write into.** `steam_users` returns all of them, sorted.
  Open question 5 — the mini PC is shared with the kids — decides whether a game
  installed by one account should appear for all, and that is a product decision,
  not one to settle by whichever directory sorts first.
- **Anything checked against a real `shortcuts.vdf`.** The sample the tests
  round-trip is one this repository constructs. It is shaped like the real thing,
  but the mini PC run should re-read a file Steam actually wrote — and the
  byte-identical round trip is exactly the assertion to point at it.
